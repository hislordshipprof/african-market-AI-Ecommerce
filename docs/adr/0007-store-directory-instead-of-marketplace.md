# 7. Store directory instead of a combined marketplace

Date: 2026-10-30 · Status: accepted · Supersedes spec D2 and the §4 Phase 2 marketplace view · Amended 2026-11-14 (#448)

Stores never share a cart or checkout. Instead of the planned combined marketplace app, the platform gets a **Store directory** (Phase 2): a public site where people search by state, city or "near me", then click through to that store's own storefront. Listing is opt-in per store. Product search across stores is deferred, because it would put competing stores' prices side by side, against stores owning their customers (ADR-0003). One customer account (ADR-0002) works at every store, but sessions are cookies scoped to each store's domain (ADR-0015), so a customer arriving from the directory signs in once more on that store's site.

## Note, 2026-11-14 (#448): owner decisions of 2026-11-11 (#447)
- No "3 stores in a metro" gate: the directory lists every listed store, wherever it is (amends ADR-0001).
- When no store is nearby, it shows the nearest stores with their distance, then the list of states. "Tell me when a store opens near me" came in D7 (#455).
- The store owner turns the listing on and writes the blurb. Listing is off by default, and a platform admin can override it. The street address is shown only to platform admins.
- Cards show distance and "delivers to you", using the store's own delivery radius only, because courier coverage is known only from a quote (ADR-0006).
- ZIP and city lookups use static US Census Gazetteer tables in Postgres, with no new runtime provider (ADR-0017). The Census geocoder resolves only full street addresses.
- The directory is served on `PLATFORM_ROOT_DOMAIN`. Until the platform name is chosen and that variable is set, the project's production alias stands in for it (decision 2026-11-23-12, #766), and the stand-in ends by itself once the variable is set:
  - Only the exact host in Vercel's `VERCEL_PROJECT_PRODUCTION_URL`, on a production deployment, and only while that value is a `*.vercel.app` alias. Vercel switches the variable to the shortest custom domain once one is attached, and store domains are attached to this project (#711), so a store's domain can never become the root. Preview, branch and deployment URLs stay "no store".
  - vercel.app has no store subdomains (Vercel's `tenant---preview` host form needs a custom preview suffix), and a path form would mean prefixing every storefront link. So stores are reached there by the existing `?store=<slug>`, which the proxy turns into the `store_override` cookie; directory links are `https://<alias>/?store=<slug>&ref=directory`. The directory home and a store's home are both `/` there, so the directory pages, `/sell` and `/admin` always serve the platform and clear the remembered store.
  - Every response on the alias carries `X-Robots-Tag: noindex`, so it never competes with the real domain in search; sitemap and canonical URLs point at the alias meanwhile.
  - The alias is an allowed sign-in host and trusted origin (exactly, no wildcard). A magic link asked for on it carries `?store=<slug>`, so it opens in a browser that never visited the store and is still redeemed only against the store it was asked on (#711).
  - Trade-off: every store on the alias shares one host, so one session cookie. A shopper signed in at one store is signed in at the others in that browser, unlike the per-store sessions above. This lasts only until the domain is set.
  - Customer messages that need a store link (order tracking, store-opened notices) still wait for the domain: they build `<slug>.<root>` links and are unchanged.
- The build steps are D1–D7 in spec §17, Phase 2.
- Built in D2 (#450): the owner sets the switch, the blurb (at most 160 characters) and up to 3 cuisine tags from a fixed list (ADR-0004) on the store-admin "Directory listing" page; staff cannot open it. The platform admin's store form overrides the switch. Every change writes an audit row and clears the directory cache tag.
- Built in D4 (#452): near me takes a ZIP code, a city ("City, ST" or "City"; a name found in several states asks which one) or the browser location, asked for only when the shopper taps "Use my location". A denied location focuses the ZIP field with a message. Stores within 50 miles come back nearest first, ranked by SQL haversine (no PostGIS, ADR-0012); with none that close the 3 nearest show with their distance, then the state list. A browser point outside every US ZIP's reach gets the state list. ZIPs and city centroids come from the 2025 Census Gazetteer files, seeded by migration `20261114230000_store_directory_gazetteer` (50 states and DC). `GET /api/directory/near` is rate-limited per browser and per IP with the Postgres limiter. Its answer carries each store's distance, never the store's own lat/lng, which would locate its street address.
- Built in D3 (#451): `/stores/<state>` and `/stores/<state>/<city>` (full names as slugs, e.g. `/stores/texas/houston`) list the listed stores there, each card with schema.org `GroceryStore` JSON-LD (city and state only). They are ISR pages (`force-static`, 300 s) read through the `store-directory` cache tag, so a listing change shows on the next request. A state or city with no listed store is a 404, so there are no thin pages. `sitemap.xml` lists the home, state and city pages; `robots.txt` points to it. The proxy serves these paths only on the root domain: store hosts get a 404 and keep their current crawl rules.
- Built in D5 (#453): each card shows "Open now" or "Closed · Opens 9 AM", worked out in the browser from the store's public hours with the order rule (`isStoreOpen`, `nextOpening`), so cached state and city pages never go stale; times are on the store's clock, with its zone named when the shopper's differs. A near me search adds the distance as text and "Delivers to you" when the shopper's point (ZIP or city centroid, or browser location) is within the store's own delivery radius (`assessRadius`, the boundary inside); the server answers with the verdict, never the radius or the store's point. Without a point the card says "Delivery". "Courier may be available" shows where the storefront offers courier delivery (registered with a courier, full address and phone, Pro plan) and the store's own delivery does not reach the shopper, since courier coverage is known only from a quote. Pickup and delivery are text badges with icons; the owner's face (a person icon until the owner adds a photo), name and story (two lines) come from the existing owner fields. Open and closed differ by word and mark shape as well as colour.
- Built in D6 (#454): every directory link to a storefront ends in `?ref=directory` (the JSON-LD `url` stays the bare storefront). On a store host the proxy then sets `came_from=directory`: a first-party, HttpOnly, SameSite=Lax cookie for 30 days that holds only that word, no store or user data. The directory host never sets it. An order placed while the cookie is there stores `acquisition_source = 'directory'` (nullable, null otherwise, a DB check allows only that value); the cookie is compared exactly. The owner's dashboard shows the count on its "Directory listing" card. A later visit without the ref keeps the cookie until it expires; there is no last-touch or cross-store tracking.
- Built in D7 (#455): when near me finds no store within 50 miles, a "Tell me when a store opens near me" panel takes a ZIP (filled in from a ZIP search) and an email or US mobile number, with a consent box whose text is stored on the request. The server action allows 5 requests an hour per browser and 20 per IP (Postgres limiter), drops a filled honeypot field without saying so, refuses a ZIP not in the Gazetteer table, and keeps one request per ZIP and contact; its answer is the same whether or not the contact was already on file. Requests live in `directory_store_requests`, platform-owned: any app_user may insert, only the platform-admin context reads or updates. The job `directory/store-request-notices` runs when a store goes into the directory (owner switch, admin override, or a listed store reactivated) and daily at 15:07 UTC; for each waiting request with a listed, active store within 50 miles of its ZIP it sends one email or text naming the nearest store, with an idempotency key per request, then marks it sent and deletes the email or phone. A send that fails leaves the request waiting for the next run. Texts need `TELNYX_FROM_NUMBER`; until it is set, text requests wait. The admin console's "Store requests" page shows waiting and sent counts by state and ZIP, never a contact; the state comes from the ZIP's 3-digit prefix and the place is the nearest Census place in that state. There is no free-text "suggest this store" field: the requests by area are the onboarding leads.

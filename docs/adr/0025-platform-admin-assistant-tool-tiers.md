# 25. Platform admin assistant tool tiers

Date: 2026-11-25 · Status: accepted (#831 built the read tier, #832 the draft and confirm tier, #833 workflow and batch cards)

## Context

The owner wants one assistant in the platform admin console that answers anything about the platform, by voice or text, and later does the steps an admin now does by hand: store creation, request checks, product and catalogue work (owner decision 2026-11-25, Build Board decision 2026-11-25-01). The store copilot (spec §8.2) already reads freely and changes nothing until the owner confirms a draft. Shopify Sidekick works the same way for merchants: it reads the store, uses the staff member's own permissions, and "can't change your live store without your approval". OWASP's LLM06 (excessive agency) and LLM01 (prompt injection) ask for least privilege, authorization outside the model, human approval before a high-impact action, and logs.

## Decision

Tools are tiered by what they can change. A tier is added by its own ticket; none skips the one before.

1. **Read (built in #831).** Reads only, through the same server function the admin screen uses (`src/lib/admin/*`, `src/lib/store-application/*`, `src/lib/support/platform-actions.ts`), never a second copy and never raw SQL. No confirm. Every call writes an `audit_logs` row (`admin_assistant.tool`, admin, tool, parameters) before it reads.
2. **Draft and confirm (built in #832).** A change is a draft card the admin confirms with one tap, on the store copilot's draft and confirm pattern. A `draft_` tool reads the record and adds a card; nothing is written but the `admin_assistant_drafts` row. The card shows what changes, from what to what, and for which store; a change that cannot be undone (an email to an applicant, a store owner or a customer) says so on the card. The one text a card carries (a support reply, a reject reason, a note, a store slug) can be edited before Confirm; the assistant never sends anything itself. The kinds are: approve or reject a store application, suspend or reactivate a store, a plan override with end date and reason, the pilot offer, a store's metro, a courier registration retry, an owner invite, the platform courier settings, a courier incident note, a review label on an AI chat, and a reply to an escalated customer message.
   - **Confirm** (`confirmAdminAssistantDraft`) runs `requirePlatformAdmin` first, so an admin without 2FA cannot confirm. Only the admin who drafted the card can confirm it. The draft must be pending and under 24 hours old. Each kind keeps a snapshot of what the change depends on (the store's status, the override, the pilot flag, the metro, the courier registration errors, the latest owner invite, the courier settings, the incident state, the chat's labels, the thread's state with its last customer message and last reply); if the record no longer matches, the card goes stale and nothing is applied. Then the confirm calls the admin screen's own function: `setStoreStatus`, `inviteStoreOwnerAction`, `saveCourierSettingsAction`, `addCourierIncidentNoteAction`, `labelConversationAction` and `replyAsPlatformAction` directly. The screen actions for applications, plan override, pilot, metro and courier retry end in a redirect, so the confirm calls the function each of them wraps: `approveStoreApplication`, `rejectStoreApplication`, `setPlanOverride`, `setPilot`, `setStoreMetro` and `retryCourierRegistration` (moved out of the store page's action so both call it). There is no store-request action to call: store requests are read only.
   - **Audit.** `admin_assistant.tool` for every tool call, `admin_assistant.draft_proposed` when a card is stored, then one of `draft_confirmed`, `draft_rejected`, `draft_stale` or `draft_refused`, each naming the admin, the kind and the parameters. The admin function writes its own row as well (for example `store.suspend`).
   - **Risk accepted.** The stale check and the apply are two steps, not one transaction, because the admin functions open their own transactions. A change in that window is caught by the admin function's own checks where it has them (status, application already decided, pilot cap); otherwise the later write wins, as it would on the screen.
3. **Workflow and batch cards (built in #833).** Still the draft and confirm tier: one card, one tap, nothing written before it. A job an admin does in several steps is one card that lists its steps; Confirm runs them in order, each through the admin screen's own function, and stops at the first that fails. Store creation is `createStore`, then `setStoreMetro` (what the redirecting `setStoreMetroAction` wraps), then `inviteStoreOwnerAction`; a product is `saveMasterProduct`, then `addProductSynonym` per synonym, then `uploadMasterProductImage` for a photo the admin attaches on the card; a recipe is `saveRecipe`. `saveMasterProduct` and `saveRecipe` create a row when no id is given, so creation and editing stay one function each; a drafted dish has origin `drafted` and is not curated until an admin marks it. A first step that fails changes nothing and the card stays open. A later step that fails leaves what was done in place and the card says which step stopped and what was done: rolling back a created store would mean deleting it, which is on the Never list. A batch card holds up to 20 items, each with its problems, and the admin unticks any before Confirm (the confirm takes the kept item ids; unticking all is refused). Each item runs through its admin function, which re-checks that item under its own lock (product status, proposal pending, pair open, category exists), so a batch card keeps no snapshot of its own and one changed item is reported as not done without stopping the rest. A new product is first matched against the catalogue with the list screen's own search, and the assistant offers the products it finds instead of drafting a duplicate. A description the assistant writes is refused at the tool when it has a health claim, a price or a place the product's origin data does not give.
   - **From the research.** Copied from Shopify Sidekick: it reads freely and "can't change your live store without your approval", and each change is shown for review before it applies; a multi-step job is one plan the merchant reviews. Copied from published agent guardrail practice (OWASP LLM06 excessive agency; tiering tools by reversibility): the gate sits before the side effect, a step that cannot be undone says so on the card, and every proposal, confirm, reject and refusal is logged. Rejected: running the steps of a workflow one tap at a time (Sidekick's per-action approval), because the owner asked for one card per job; automatic rollback of a half-done workflow, because undoing a store means deleting it; and proactive suggestions (Sidekick Pulse), which stay unbuilt and will arrive as cards when built.
4. **Never.** No tool or draft kind exists, in any tier, to create or remove platform admins, change a user's role, change 2FA or security settings, change Stripe or payout settings, read or set secrets, or delete stores or users. The prompt tells the admin so; the absence of the tool is the control, and a confirm refuses any draft row whose kind is not in the list (`admin_assistant.draft_refused`).

Every tier runs only behind `requirePlatformAdmin` (signed in, platform admin, 2FA verified), on the copilot engine's spend gate, rate limit, lease, history and step caps. Tool results are data, never instructions. The model writes no links and no numbers of its own: links are built from tool rows, and a reply with a number no tool returned is refused.

## Consequences

- A later ticket adds a draft kind with its snapshot (or, for a batch, its admin function's own per-item check) and its admin function; the confirm, the card and the audit rows stay as they are. The card can show steps, items to untick and a photo field; the confirm takes the edited text, the kept items and a photo.
- Proactive suggestions (Sidekick's Pulse) are not built yet; when built they arrive as draft cards, never as changes.
- `platform_totals` is the one read with no admin screen of its own; it adds the store analytics figures (`salesRows`, `salesView`, #498) across stores rather than computing sales a second way.
